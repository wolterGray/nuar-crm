# NUAR CRM: диагностика production-уведомлений

Дата отчёта: 17.10.2026. Production-проверка: 18.10.2026. Режим: read only.

## Краткое резюме

Production PostgreSQL на Hetzner проверен прямым `psql`-подключением 18.10.2026.
Диагностика выполнена в транзакции `READ ONLY` с итоговым `ROLLBACK`; генераторы,
API, миграции и фоновые процессы не запускались. Обезличенный исходный результат сохранён в
[`notification-production-results-2026-10-18.txt`](notification-production-results-2026-10-18.txt).

Фактически в базе находятся 277 server events: 227 активных, 45 разрешённых и 5 отклонённых.
Из 227 активных событий 121 является актуальной маркетинговой возможностью, 8 требует действия,
а 98 уже неактуальны по состоянию связанного объекта. Внутри устаревших событий есть 11 лишних
копий переносов; это пересекающийся показатель, а не дополнительная категория.

Код подтверждает механизм появления большого числа:

- frontend запрашивает максимум 40 активных server events;
- затем добавляет вычисляемые локально финансовые ошибки, незакрытые визиты, дни рождения, прогноз и undo;
- красный badge считает все видимые `critical` и `action` строки;
- server `critical` остаётся critical, а `high` или `score >= 70` становится action;
- возможности продаж и обычные рабочие события поэтому попадают в тревожный счётчик.

Число 44 наиболее правдоподобно складывается из максимальных 40 server events, которые загружает
frontend, и четырёх локальных сигналов. Production подтверждает, что первые 40 server events по
текущей сортировке все преобразуются в `action`. Точное воспроизведение оставшихся четырёх требует
read-only snapshot уже загруженного состояния frontend; запускать API-генератор ради этого нельзя.
Результат не подгонялся под 44.

Три изменения с наибольшим ожидаемым эффектом:

1. Красный badge считать только по актуальным `critical/action`, исключив opportunities/information.
2. Перенести оценку актуальности и автозакрытие в единый backend registry типов.
3. Убрать mutation-generator из frontend polling и запускать его одним cron/worker.

## 1. Точный механизм счётчика

### Серверная часть

1. `useClientAlerts.refreshServerEvents()` вызывает `generateNotificationEvents()`, а затем `fetchNotificationEvents({limit: 40, status: "active"})`.
2. Backend `listNotificationEvents()` считает глобально активными статусы `new`, `seen`, `snoozed`, но исключает snoozed до наступления `snoozedUntil`.
3. `listNotificationEventsForUser()` создаёт/читает `NotificationRecipient` и повторно фильтрует состояние конкретного пользователя.
4. Server event преобразуется в frontend alert функцией `mapServerEventToAlert()`.
5. `critical` остаётся `critical`; `high` или `score >= 70` преобразуется в `action`; остальные становятся `info`.

Файлы:

- `src/hooks/useClientAlerts.js:289-335`
- `backend/services/notificationEventsService.js:233-280`
- `backend/services/notificationEventsService.js:612-674`

### Локальная часть

`buildAlertCenter()` вычисляет сигналы из загруженного состояния CRM. Когда server доступен, `useClientAlerts()` удаляет из локального списка типы calendar, task, supply, package, certificate и inactive. Остаются:

- `financial_quality`;
- `unclosed_visit`;
- `birthday`;
- `forecast`;
- `undo`.

При недоступном server остаются все локальные типы.

Файлы:

- `src/utils/alertCenter.js:116-560`
- `src/hooks/useClientAlerts.js:399-417`

### Число на колокольчике

`NotificationDrawer` получает `allAlerts`, повторно применяет временное локальное скрытие и вызывает `getNotificationDrawerCounts()`:

```text
badgeCount = visibleAlerts.filter(priority is critical or action).length
```

Это количество отображаемых строк после группировки, а не количество непрочитанных сообщений и не всегда количество underlying проблем. Один aggregate считается одной строкой.

Файлы:

- `src/utils/notificationDrawerCounts.js`
- `src/components/NotificationDrawer.jsx:112-155`

### Влияние статусов

| Статус | Попадает в active API | Влияет на badge |
|---|---|---|
| `new` | Да | Да, если mapped priority critical/action |
| `seen` | Да | Да; прочтение не решает проблему |
| `snoozed` с будущей датой | Нет | Нет |
| `snoozed` с истёкшей датой | Да | Да |
| `resolved` | Нет | Нет |
| `dismissed` | Нет | Нет |

Локальные dismiss/snooze хранятся в local storage и могут различаться между устройствами. Временное swipe-hide существует только в памяти текущего UI.

## 2. Ограничение 40

Frontend запрашивает только 40 событий. Backend сначала берёт до 100 кандидатов, сортируя по `score desc, createdAt desc`, затем возвращает первые 40 после visit-фильтрации.

Следствия:

- UI может не показывать все active server events;
- badge может быть меньше реального числа active action events;
- старые low-score события могут никогда не попасть в frontend;
- число около 44 не означает, что server events ровно 40, но архитектурно допускает `40 server + локальные action/critical`.

## 3. Возможные пересечения источников

При `serverConnected=true` основные совпадающие типы локально исключаются. Пересечение всё же возможно:

- во время переключения между fallback и server connected;
- для одного визита, представленного как `calendar_entry` и как `visit`;
- для финансовой ошибки и незакрытого визита об одном визите: это разные условия, но один бизнес-объект;
- для локального popup/toast ближайшего визита и server event;
- на разных устройствах из-за локального состояния hide/dismiss.

## 5. Безопасный read-only SQL для Hetzner

Актуальный скрипт вынесен в
[`docs/sql/notification-production-readonly.sql`](sql/notification-production-readonly.sql).
Это единственный вариант, который следует запускать. Он:

- открывает транзакцию `READ ONLY` и завершает её через `ROLLBACK`;
- ограничивает время запроса и ожидание блокировок;
- не выводит имена, телефоны, тексты сообщений, payload, ID клиентов и объектов;
- не выводит значения fingerprint, а только агрегированное число нарушений уникальности;
- содержит только агрегирующие `SELECT` по таблицам, сверенным с текущей Prisma schema.

Старый встроенный вариант удалён: он мог раскрыть технические идентификаторы объектов.
Если production schema отличается от текущей Prisma schema, выполнение остановится благодаря
`ON_ERROR_STOP`; после этого сначала нужно отдельно сверить структуру затронутой таблицы.

|---|---|---|

| Заявка сайта | Требует действий | Пока не обработана |

| Неактивный клиент | Возможность | Маркетинговая реактивация |
| Сертификат истекает/мал баланс | Возможность | Продажа/использование |
| Waitlist | Возможность | Подбор освободившегося времени |
| День рождения | Возможность | Коммуникация с клиентом |
| Новая/отменённая/перенесённая запись | Информационное | Action только при отдельном бизнес-условии |
| Ближайший визит | Информационное | Не должен постоянно увеличивать badge |

## 7. Правила автозакрытия

| Тип | Создание/активность | Автозакрытие | Новый цикл и dedup |
|---|---|---|---|
| task overdue | due прошёл, task active | completed/cancelled/archive или due перенесён | `task:{id}:overdue:{occurrence}` |
| visit upcoming | визит в горизонте | время + grace прошло или terminal status | один event на visit occurrence |
| unclosed visit | время прошло, status active | terminal status | стабильный visit ID |
| supply low | stock <= min | stock > min или позиция архивна | новый occurrence после восстановления и повторного падения |
| package ending | active и remaining <= threshold | остаток выше порога или terminal package | package ID + occurrence |
| certificate | active и порог срока/баланса | использован, продлён, закрыт/истёк | certificate ID + condition + occurrence |
| inactive client | последний completed visit старше порога | новый completed visit | client ID + inactivity cycle |
| waitlist | status active | matched/closed/cancelled/done | waitlist entry ID |
| finance quality | нарушение реально существует | связь/начисление исправлено | entity + issue type |
| booking request | заявка не обработана | accepted/rejected/closed | booking ID |

## 8. Новая логика колокольчика

```text
redBadge = count(
  event.active
  AND event.category IN ('critical', 'action')
  AND recipient.snoozedUntil <= now
)
```

- `seen` не уменьшает badge: прочитано не означает решено.
- Opportunities и information показываются без красного числа.
- Aggregation меняет представление, но не underlying count.
- Critical желательно отображать отдельным индикатором внутри центра.
- Opportunities показывать одной сводной строкой на тип с раскрытием списка.
- Information хранить в истории с TTL, не на основном экране.

## 9. Пошаговый безопасный план

1. Согласовать каталог типов и классификацию на полученных production-агрегатах.
2. Зафиксировать read-only frontend snapshot, чтобы точно подтвердить четыре локальных сигнала в badge 44.
3. Добавить additive поля category/conditionKey/occurrence/active без удаления старых данных.
4. Реализовать server resolver + auto-close для одного типа и сравнить с текущим контуром.
5. Перенести generation в единственный cron/worker; frontend оставить read-only.
6. Добавить aggregate counts endpoint из одного snapshot.
7. Переключить badge за feature flag.
8. По одному переносить frontend generators на backend.
9. После периода сравнения отключить локальные persisted alerts, оставив toast/undo отдельно.
10. Только после проверки данных упростить UI до «Требуют внимания / Возможности / История».
