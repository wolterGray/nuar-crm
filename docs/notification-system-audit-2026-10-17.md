# NUAR CRM: аудит системы уведомлений

Дата аудита: 17.10.2026. Этап: диагностика и проектирование, без изменения приложения и данных.

## 1. Резюме

В CRM одновременно работают два контура уведомлений:

1. `buildAlertCenter()` динамически вычисляет сигналы в браузере из загруженных визитов, задач, клиентов, пакетов, сертификатов и склада. Прочтение для этих сигналов отсутствует, скрытие и snooze хранятся локально.
2. Backend хранит `NotificationEvent`, персональное состояние `NotificationRecipient` и доставки `NotificationDelivery`. Эти события генерируются при бизнес-операциях и полным сканированием данных.

Frontend объединяет контуры в `useClientAlerts()`. При доступном backend он исключает часть локальных типов, но оставляет финансовые ошибки, незакрытые визиты, дни рождения, прогноз и undo. Это переходная архитектура, а не единый источник истины.

Главная причина тревожного счётчика: badge считает одновременно `critical` и `action`; серверные `high` и события со `score >= 70` преобразуются в `action`. В эти категории попадают не только аварии, но и обычные задачи, склад, пакеты, реактивация клиентов и ближайшие визиты.

Ситуация `44 из 45` правдоподобно складывается из максимум 40 серверных событий (`fetchNotificationEvents({limit: 40})`) и локально рассчитанных сигналов. Точный состав конкретных 44 можно подтвердить только read-only выборкой production-БД и снимком входных данных frontend.

### Обновление и кэширование

- Локальный центр пересчитывается через `useMemo` при изменении любых исходных коллекций.
- Backend generation вызывается каждым открытым frontend-клиентом сразу и далее каждые 5 минут.
- Server events запрашиваются с лимитом 40.
- Локальные dismiss/snooze сохраняются в local storage через `useCrmLocalPersistence`.
- Серверные seen/snooze/dismiss сохраняются в `NotificationRecipient`.
- Дополнительно `NotificationDrawer` временно скрывает карточку только в памяти на 30 минут/день/неделю для мгновенной реакции UI.

## 4. Подтверждённые проблемы

### Критические

1. Нет единого источника истины. Динамические frontend alerts и persisted backend events используют разные пороги, ID, приоритеты и жизненные циклы.
2. Backend generator вызывается из браузера каждые 5 минут. GET-подобное обновление интерфейса инициирует записи в БД и может одновременно выполняться с нескольких устройств.
3. Генератор создаёт/обновляет события, но почти не закрывает условия, которые перестали быть истинными. Реализовано специальное закрытие только устаревшего `visit_upcoming` и перехода важной задачи due -> overdue.
4. `upsertNotificationEvent()` при повторном цикле обновляет содержимое, но не определяет новую occurrence и не возвращает `resolved/dismissed` событие в `new`. Это предотвращает шум, но навсегда подавляет реально повторившееся событие с тем же fingerprint.

### Высокие

5. Счётчик измеряет строки после группировки, а не нерешённые бизнес-события: агрегат из 20 проблем считается одной строкой. В другом месте badge может считаться до локальной/после серверной фильтрации.
6. `high` либо `score >= 70` преобразуется в `action`. Score включает коммерческую ценность и денежное влияние, поэтому маркетинговая ценность способна превратить возможность в тревожный badge.
7. Все просроченные локальные задачи помечаются `critical`, даже если задача не главная и не блокирует работу.
8. Нулевой пакет помечается `critical`, хотя это продажная возможность, а не авария.
9. Неактивный клиент после двойного порога становится `action`, поэтому массовая реактивация раздувает тревожный счётчик.
10. Настройки локального центра и server generator расходятся: frontend переключатели не применяются ко всем серверным типам при генерации.
11. `/notification-events/generate` доступен любому активному JWT-пользователю, а не только owner/worker, и выполняет тяжёлый scan + writes.

### Средние

12. Порог пакета различается: <=2 frontend, <=1 backend. Порог сертификата различается: процент frontend, фиксированные 50 zł backend.
13. Порог неактивности различается: frontend settings default 14 дней; backend fallback 45 дней и использует последний `Visit.scheduledAt`, не подтверждая completed status.
14. Backend получает максимум 100 сущностей каждого типа и frontend максимум 40 событий. Полный список и badge зависят от лимитов, а не только от актуальности.
15. Открытие drawer массово помечает все server events как seen. Это корректно для ознакомления, но `seen` визуально почти не отделён от нерешённого состояния.
16. Swipe «закрыть» фактически делает snooze на 30 минут, а крестик делает permanent dismiss. Термины интерфейса не соответствуют модели.
17. Локально скрытые динамические события привязаны к local storage устройства; на другом устройстве они появляются снова.
18. Даты формируются частично в локальном timezone процесса/browser. Явная `Europe/Warsaw` используется в Push-тексте, но не во всех генераторах.

## 5. Дублирование

### Реальная защита

- `NotificationEvent.fingerprint` уникален.
- `NotificationRecipient` уникален по `(event, user)`.
- Web Push delivery уникален по `(event, subscription)` через `deduplicationKey`.
- Повторный scan обновляет существующее событие через upsert.

### Риски и объяснение повторов «Пакет закончился»

- Backend fingerprint пакета включает ID пакета: `client-package:{packageId}:ending`. Два законченных пакета одного клиента являются разными объектами, хотя UI показывает почти одинаковый текст. Это не технический дубль, но визуально выглядит как дубль.
- Frontend ID включает `remainingVisits`: `package-balance-{packageId}-{remaining}`. При изменении остатка появляется другая логическая версия, а старый dismiss не применится к новой.
- Один пакет может существовать одновременно как локальный alert и server event во время ошибок backend/fallback или переключения `serverConnected`.
- Visit может иметь два источника сущностей (`calendar_entry` и `visit`) и разные fingerprint `visit:*` / `visit-record:*`; если обе операции отражают одну запись, пользователь увидит два бизнес-события.
- Reschedule fingerprint включает новую дату/время. Это правильно для разных переносов, но повторный перенос A -> B, затем C -> B повторно использует старую occurrence и может остаться dismissed.

Предлагаемый ключ: `(tenant, eventType, entityType, entityId, conditionKey, occurrenceKey)`. `conditionKey` описывает устойчивое условие, `occurrenceKey` меняется только после подтверждённого завершения предыдущего цикла.

## 6. Новая минимальная модель

Сохранить существующие таблицы и расширить их, не делать rewrite.

### Событие

- `category`: `critical | action | opportunity | information`.
- `conditionKey`: стабильная идентичность условия.
- `occurrence`: номер повторного цикла.
- `sourceUpdatedAt` и `lastEvaluatedAt`.
- `active`: истинно только пока источник подтверждает условие.
- `resolvedReason`: `condition_cleared | user_completed | expired | source_deleted`.
- `expiresAt` для информационных событий.

### Пользовательское состояние

Оставить в `NotificationRecipient`:

- `unread/read` отдельно от состояния события;
- `snoozedUntil`;
- `dismissedAt` только для opportunity/information;
- `acknowledgedAt` при необходимости для critical;
- не хранить «resolved» как пользовательское состояние, если проблема определяется бизнес-объектом.

### Инвариант

Одно активное условие = одно активное событие. Повторная оценка обновляет его. Когда условие исчезает, событие закрывается. Если условие возникло снова после закрытия, создаётся новая occurrence.

## 7. Счётчик и информационная архитектура

Основной badge:

`active && category in (critical, action) && recipient not snoozed`

- Opportunities и information не входят в красный badge.
- Read не уменьшает badge, потому что проблема не решена.
- Badge считает реальные child events, UI может показывать их одной группой.
- Critical можно показывать отдельным красным индикатором/точкой, не смешивая с общим числом.

Центр:

1. **Требуют внимания**: critical + action, сначала critical.
2. **Возможности**: реактивация, пакеты, сертификаты, waitlist, дни рождения.
3. **История**: resolved и information с ограниченным сроком хранения.

Основной экран не нуждается в семи фильтрах. Группировать стоит массовые homogeneous opportunities и склад; финансовые ошибки, конфликт записи и конкретную просроченную задачу оставлять индивидуальными.

## 8. План миграции

1. Зафиксировать каталог типов и resolver для каждого типа в одном backend registry.
2. Добавить nullable-поля новой модели и индексы безопасной additive migration.
3. Backfill существующих events: category, conditionKey, occurrence=1; данные не удалять.
4. Вынести generation из frontend polling в один cron/worker. Frontend только читает события.
5. Перенести локальные финансовые, визитные и остальные генераторы на backend поэтапно; до переключения оставить feature flag.
6. Для каждого resolver реализовать evaluate + auto-resolve в одной транзакционной процедуре.
7. Перевести badge на server aggregate endpoint, возвращающий counts и группы из одного snapshot.
8. Упростить drawer до трёх разделов после стабилизации данных.
9. После периода параллельного сравнения отключить local generation, оставив только временные undo/toast события вне центра.

Миграция не должна удалять текущие события. Старые `dismissed/resolved` остаются в истории.

## 9. Проверки

- Повторный generator run не увеличивает число активных событий.
- Изменение payload обновляет событие без новой копии.
- После auto-resolve повторное возникновение создаёт occurrence +1.
- Два разных пакета одного клиента остаются разными событиями.
- Completed visit закрывает inactive, но будущая запись не закрывает его.
- Оплата закрывает unpaid/financial condition только после подтверждённой транзакции.
- Completed task закрывает overdue; перенос due date пересчитывает категорию.
- Stock replenishment закрывает low/out-of-stock.
- Snooze одного пользователя не скрывает событие у другого.
- Read не уменьшает action badge; resolve уменьшает.
- Opportunities не увеличивают красный badge.
- Multi-device выдаёт одинаковые counts.
- Одновременный cron run не создаёт дубли.
- Все локальные даты проверяются на границах DST в `Europe/Warsaw`.
- Не-owner не может запускать generation и видеть чужие события.
- Ошибка Push не откатывает бизнес-операцию; retry не создаёт вторую delivery.

## 10. Что проверить read-only в production

Для точного объяснения текущих `44` нужны агрегаты без персональных данных:

- active events по `type`, `priority`, recipient status;
- распределение score и число `score >= 70`;
- одинаковые `(type, entityType, entityId)` с разными fingerprint;
- пакеты одного clientId с несколькими active `package_ending`;
- события, источник которых уже terminal/отсутствует;
- события старше 7/30 дней, всё ещё active;
- число active events сверх frontend limit 40.

До этой проверки нельзя утверждать, какие именно записи образуют число 44, но кодовая причина завышенной срочности подтверждена.
